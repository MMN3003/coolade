## ۱. چرا محصول جدید؟ — درس‌های v1

v1 (EcoCode Gateway) یک «گیت‌وی چت‌محور» بود: چت وب + کلید API + سهمیه، که ورک‌اسپیس و فایل و سندباکس به‌تدریج و با اصلاحیه بهش چسبانده شد. جمع‌بندی مالک محصول: **عملاً شکست خورد** و ریشهٔ اصلی، **شکنندگی فنی** بود، نه نبود نیاز.

درس‌ها — این‌ها قواعد طراحی v2 هستند، نه یادداشت تاریخی:

| # | درس | ریشه در v1 | قاعدهٔ v2 |
|---|---|---|---|
| **L1** | **هرگز بین دو paradigm ترجمه نکن** | مسیر passthrough هر درخواست HTTP را در یک نوبت تک‌شات CLI می‌پیچید: tool-ها پل نمی‌شدند، تاریخچه تخت می‌شد، هر تغییر آپ‌استریم زنجیره را می‌شکست | هر مسیر روی primitive بومی خودش: چت وب = اجرای headless خود Claude Code؛ کلید API = relay خام HTTP برای کلاینتی که خودش هویت درست می‌فرستد. لایهٔ «مبدل» نداریم. |
| **L2** | **واحد محصول درست را انتخاب کن** | واحد اصلی «گفتگو» بود؛ فایل/ورک‌اسپیس/IDE ضمیمه‌های بعدی بودند و هر بار وصله شدند | واحد اصلی v2 = **ورک‌اسپیس** (فضای فایل ایزوله + ایجنت زنده). چت و IDE دو رابطِ همان یک چیزند. |
| **L3** | **هسته قبل از فیچر** | تیم‌ها، حافظهٔ مشترک، slash commands و... در حالی اضافه شدند که مسیر اصلی (passthrough) ناقص بود | هیچ فیچری وارد نمی‌شود تا سناریوی اصلی end-to-end پایدار نباشد؛ هر کامپوننت جدید باید توجیه عملیاتی داشته باشد. |
| **L4** | **ایزولاسیون از روز اول** | سندباکس در اصلاحیهٔ ۶ رسید؛ تا آن موقع Bash/git خاموش بود و محصولِ dev عملاً بی‌دست‌وپا | envelope ایزولاسیون (شبکهٔ internal + egress allowlist + بدون credential) جزو هستهٔ P1 است، نه فاز بعد. |
| **L5** | **آنچه کار کرد را نگه دار** | refresh توکن، ترجمهٔ stream-json، ledger سهمیهٔ دوسقفه، auth/LDAP، بقای نوبت مستقل از مرورگر — این‌ها بعد از اصلاحیه‌ها پایدار شدند | این اجزا عیناً منتقل می‌شوند (§۱۱)؛ دوباره طراحی نمی‌شوند. |

## ۲. چشم‌انداز

> **هر کارمند سازمان یک فضای کاری امن با یک ایجنت Claude Code کنارش دارد — توسعه‌دهنده با IDE کامل تحت وب، کارمند عمومی با چت ساده — هر دو روی یک زیرساخت واحد.**

مفهوم مرکزی: **Workspace** = فضای فایل ایزوله + ایجنت + رابط. دو گونه دارد:

- **ورک‌اسپیس ریپویی** (توسعه‌دهنده): متصل به یک ریپوی GitLab سازمان؛ رابطش IDE وب (VS Code واقعی در مرورگر) + پنل چت با ایجنت در همان پوشه؛ خروجی کار به‌صورت برنچ/MR به گیت‌لب برمی‌گردد.
- **ورک‌اسپیس شخصی** (کاربر عمومی): بدون ریپو؛ رابطش همان چت سادهٔ v1 است — فایل می‌سازد، فایل می‌گیرد، تاریخچه دارد. از دید کاربر «چت سازمانی» است؛ از دید معماری همان ورک‌اسپیس است با پوستهٔ ساده‌تر.

این یکپارچگی، دقیقاً وارونهٔ v1 است: به‌جای این‌که به چت، فایل بچسبانیم، به فضای کاری، چت داده‌ایم.

## ۳. تصمیم‌های معماری سطح محصول (رکورد تصمیم)

### ۳.۱ کد کجا کار می‌شود؟ — «ریموت» بررسی و رد شد

سؤال مالک محصول: آیا می‌شود Claude Code را از سرور مرکزی به کدِ روی سیستم دیگر وصل کرد؟ سه راه فنی بررسی شد:

| راه | ارزیابی |
|---|---|
| اجرای CLI روی خود ماشین مقصد (کاربر SSH بزند و آن‌جا `claude` اجرا کند) | کار می‌کند ولی محصول وب نیست؛ به‌عنوان مسیر مکمل کلید API (A1) پوشش داده می‌شود |
| mount فایل‌سیستم ریموت روی سرور (SSHFS/NFS) | شکننده و کند: هر Read/Grep ایجنت یک رفت‌وبرگشت شبکه؛ قطعی mount = سشن خراب؛ مدیریت دسترسی چندکاربره پرریسک — **رد** |
| ابزارهای ریموت از طریق MCP (سرویس روی ماشین مقصد) | معمارانه تمیز ولی یعنی خاموش‌کردن ابزارهای native ایجنت و افت محسوس کیفیت + یک کامپوننت توزیع‌شدهٔ جدید (نقض L3) — **رد** |

**تصمیم:** کد روی سرور کار می‌شود. منبع حقیقت GitLab سازمان (`git.ecobin.ir`) است؛ ورک‌اسپیس clone موقتی/ماندگار از آن است و خروجی همیشه با git برمی‌گردد. این همان الگویی است که صنعت به آن رسیده (GitHub Codespaces، Claude Code on the web) — ما نسخهٔ on-premise آن را می‌سازیم.

### ۳.۲ IDE و ایجنت روی یک فایل‌سیستم

code-server (VS Code وب) و ایجنت در **همان volume ورک‌اسپیس** کار می‌کنند: کاربر در IDE فایل عوض می‌کند، ایجنت همان لحظه می‌بیند؛ ایجنت کد می‌نویسد، در IDE و پنل diff دیده می‌شود. دو رابط، یک حقیقت.

### ۳.۳ ماندگاری ورک‌اسپیس: per (کاربر × ریپو)

مدل Codespaces: هر کاربر برای هر ریپو حداکثر یک ورک‌اسپیس زنده دارد که بین سشن‌ها می‌ماند (کش build و `node_modules` و برنچ کاری حفظ می‌شود). کنترل هزینه با: توقف خودکار در بیکاری (idle-stop)، سهمیهٔ دیسک، و پاک‌سازی با اخطار. ورک‌اسپیس متوقف‌شده با یک کلیک (و کمی صبر) دوباره بالا می‌آید.

### ۳.۴ کلید API: فقط relay خام — پایان CLI-wrapping

کلید API شخصی فقط برای کلاینت‌هایی است که خودشان درخواست Anthropic-شکلِ با هویت درست می‌فرستند — در عمل یعنی **Claude Code CLI روی ماشین خود توسعه‌دهنده**. گیت‌وی فقط توکن آپ‌استریم را تزریق و درخواست را **بدون دستکاری** عبور می‌دهد و usage را از رویدادهای SSE برمی‌دارد. مسیر «CLI-wrapping برای کلاینت‌های خارجی» (Cline و OpenAI-سازگارها) که منبع اصلی شکنندگی v1 بود، **حذف قطعی** است (تصمیم ۲، §۱۰)؛ فقط در صورت تقاضای واقعی آینده و صرفاً با راه‌حل غیر-wrapping بازبینی می‌شود.

| نقش | مقیاس فاز اول | نیازها |
|---|---|---|
| **توسعه‌دهنده** | زیر ۱۰ نفر | ورک‌اسپیس ریپویی: IDE وب + چت ایجنت + ترمینال sandboxed؛ push/MR؛ در کنارش امکان اجرای Claude Code روی ماشین خودش با کلید شخصی |
| **کاربر عمومی واحدها** | ~۲۰ نفر | چت فارسی با ایجنت، ساخت/آپلود/دانلود فایل، تاریخچه — روی ورک‌اسپیس شخصی |
| **ادمین IT** | ۱–۲ نفر | مدیریت کاربران/LDAP، سهمیه و ACL مدل، پایش مصرف و ظرفیت، وضعیت اتصال آپ‌استریم، audit |

## ۵. الزامات کارکردی

### W — هستهٔ ورک‌اسپیس
- **W1:** ساخت ورک‌اسپیس ریپویی: انتخاب ریپو (از ریپوهای مجاز کاربر در گیت‌لب، با توکن خودش) + برنچ مبنا → clone در volume اختصاصی. هر ورک‌اسپیس دقیقاً **یک ریپو** (تصمیم ۵، §۱۰)؛ image پایهٔ واحد و ابزارهای هر پروژه داخل خود sandbox نصب می‌شود (تصمیم ۶، §۱۰).
- **W2:** ماندگاری per (کاربر × ریپو)؛ idle-stop خودکار (پیش‌فرض ۳۰ دقیقه بی‌فعالیتی، قابل تنظیم ادمین) و resume شفاف؛ نمایش وضعیت (running / stopped / در حال آماده‌سازی) در UI.
- **W3:** envelope ایزولاسیون از روز اول: کانتینر per-workspace، شبکهٔ internal، egress فقط به آپ‌استریم مدل و `git.ecobin.ir` (+ منبع extension)، بدون هیچ credential بک‌اند، سقف mem/cpu/pids، `no-new-privileges`.
- **W4:** **سهمیهٔ فضای ذخیره‌سازی per-user** (تصمیم ۳، §۱۰): ادمین در تنظیمات برای هر کاربر سقف کل فضا (مجموع ورک‌اسپیس‌ها + فایل‌های چت) تعیین می‌کند؛ کاربر نوار مصرف فضا را می‌بیند. با پر شدن فضا، ساخت ورک‌اسپیس/فایل جدید مسدود و به کاربر گفته می‌شود **خودش** پاک‌سازی کند: حذف چت‌ها/ورک‌اسپیس‌های قدیمی، یا تنظیم retention شخصی خودش (پاک‌سازی خودکار ورک‌اسپیس‌های متروک؛ پیش‌فرض ۳۰ روز با دو اخطار). برنچ‌های push نشده هرگز بی‌اخطار حذف نمی‌شوند.
- **W5:** ورک‌اسپیس شخصی (بدون ریپو) برای همهٔ کاربران — بستر چت عمومی؛ همان envelope با egress حداقلی.
- **W6:** سقف سراسری ورک‌اسپیس‌های فعال هم‌زمان؛ بالاتر از ظرفیت → پیام صف/ظرفیت شفاف.
- **W7:** حذف ورک‌اسپیس توسط خود کاربر؛ غیرفعال‌شدن کاربر → توقف فوری ورک‌اسپیس‌ها.

### I — رابط IDE (ورک‌اسپیس ریپویی)
- **I1:** VS Code وب (code-server) به ازای هر کاربر، گِیت‌شده با نشست EcoCode — بدون پسورد جداگانه؛ هیچ کاربری ورک‌اسپیس دیگری را نمی‌بیند.
- **I2:** IDE به volume همان ورک‌اسپیس وصل است؛ ترمینال integrated داخل همان sandbox (اینترنت فقط از egress allowlist).
- **I3:** IDE و چت در یک صفحهٔ محصول کنار هم (split view)؛ سوییچ روان بین «گفتگو با ایجنت» و «ویرایش دستی».
- **I4:** نصب extension فقط از منبع allowlist شده (open-vsx از مسیر egress).

### C — چت ایجنت (هر دو گونهٔ ورک‌اسپیس)
- **C1:** چت فارسی RTL؛ هر نوبت = اجرای headless خود Claude Code CLI در cwd ورک‌اسپیس (primitive بومی — L1).
- **C2:** استریم پاسخ + **بقای نوبت مستقل از مرورگر** + retry نوبت شکست‌خورده (پورت مستقیم از v1).
- **C3:** تاریخچهٔ گفتگوها per-workspace؛ جستجو، عنوان، حذف.
- **C4:** انتخاب مدل از مدل‌های مجاز کاربر + سطح تفکر سه‌حالته (پورت از v1).
- **C5:** پس از هر نوبت ایجنت، خلاصهٔ فایل‌های تغییرکرده + diff قابل مشاهده در UI.
- **C6:** آپلود فایل به ورک‌اسپیس و دانلود خروجی‌ها از همان چت (تجربهٔ کاربر عمومی v1 حفظ می‌شود).

### G — یکپارچگی گیت‌لب (ورک‌اسپیس ریپویی)
- **G1:** هر توسعه‌دهنده یک‌بار PAT شخصی گیت‌لب (scope حداقلی repo) ثبت می‌کند؛ رمزشده ذخیره، قابل تعویض/حذف.
- **G2:** clone/push فقط با توکن خود کاربر → دسترسی ریپوها همان دسترسی گیت‌لب خودش است و commit به نام خودش ثبت می‌شود؛ EcoCode توکن سراسری گیت‌لب ندارد.
- **G3:** push پیش‌فرض به برنچ با پیشوند قراردادی (`ecocode/…`)؛ push به برنچ‌های محافظت‌شده ممنوع؛ UI لینک ساخت MR می‌دهد. merge فقط از مسیر review خود گیت‌لب.
- **G4:** توکن گیت‌لب فقط داخل sandbox ورک‌اسپیس همان کاربر تزریق می‌شود؛ egress allowlist مقصدش را به `git.ecobin.ir` محدود می‌کند.

### V — حاکمیت (پورت از v1)
- **V1:** auth با LDAP سازمان + کاربر محلی؛ نقش‌های `admin`/`user`.
- **V2:** ACL مدل per-user.
- **V3:** سهمیهٔ «توکن وزن‌دار» با دو سقف هم‌زمان: دوره‌ای (هفتگی) + غلتان ۵ساعته؛ رد شفاف با پیام فارسی و زمان آزادشدن.
- **V4:** داشبورد مصرف کاربر (روند، تفکیک مدل/سطح) و ادمین (کل سازمان، drill-down per-user، CSV).
- **V5:** audit log: لاگین، ساخت/ابطال کلید و توکن، ساخت/حذف ورک‌اسپیس، push، رد به دلیل سقف.
- **V6:** مدیریت اتصال آپ‌استریم: seed از فایل CLI + refresh خودکار توکن + نمایش وضعیت/لیمیت اکانت در پنل ادمین.

### A — کلید API شخصی (مسیر مکمل CLI)
- **A1:** کلید شخصی برای اجرای Claude Code CLI روی ماشین خود توسعه‌دهنده؛ گیت‌وی relay خام است (§۳.۴)؛ usage از SSE ثبت می‌شود.
- **A2:** سهمیه و ACL همان کاربر روی این مسیر هم اعمال می‌شود؛ در گزارش‌ها با برچسب مسیر تفکیک می‌شود.
- **A3:** صفحهٔ onboarding: راهنمای گام‌به‌گام + قطعهٔ کانفیگ آمادهٔ کپی (`ANTHROPIC_BASE_URL` + کلید).

## ۶. مدل سهمیه

همان مدل v1 (اثبات‌شده): `مصرف = ورودی×ضریب مدل + خروجی×ضریب` با ضریب کاهش‌یافتهٔ cache-read؛ واحد نمایش «امتیاز»؛ ضرایب دست ادمین. جزئیات در سند فنی v2.

| حوزه | الزام |
|---|---|

## ۱۲. سفر کاربر (User Journeys)

سناریوهای سرتاسری برای هر persona. اینها مبنای معیار پذیرش (§۱۳) و نقشهٔ صفحات (§۱۴)اند.

### ۱۲.۱ توسعه‌دهنده — سشن کدنویسی وب (مسیر اصلی dev)
1. لاگین به EcoCode Studio (LDAP یا محلی).
2. بار اول: در پروفایل، **توکن گیت‌لب شخصی (PAT)** را ثبت می‌کند (یک‌بار).
3. «ورک‌اسپیس جدید» → از لیست ریپوهای مجازش در گیت‌لب یکی + برنچ مبنا را انتخاب می‌کند.
4. صفحهٔ «در حال آماده‌سازی» را می‌بیند (clone + بالا آمدن کانتینر) — ده‌ها ثانیه.
5. IDE (VS Code وب) با پنل **Claude Code به‌عنوان چت پیش‌فرض** باز می‌شود؛ درخت فایل ریپو آماده است.
6. در چت به فارسی می‌گوید چه می‌خواهد؛ ایجنت فایل‌ها را می‌خواند، ویرایش می‌کند، diff نشان می‌دهد، در ترمینال تست می‌زند.
7. تغییرات را بررسی/تأیید می‌کند؛ سپس **push به برنچ `ecocode/...`** → UI لینک ساخت Merge Request در گیت‌لب می‌دهد.
8. سشن را می‌بندد؛ ورک‌اسپیس بعد از بیکاری خودکار stop می‌شود؛ دفعهٔ بعد در چند ثانیه resume می‌شود (کش build حفظ است).

### ۱۲.۲ توسعه‌دهنده — مسیر CLI روی ماشین خودش (مکمل)
1. در صفحهٔ «کلید API»، کلید شخصی می‌سازد و **قطعهٔ کانفیگ آماده** را کپی می‌کند.
2. روی ماشین خودش `ANTHROPIC_BASE_URL` + کلید را set و `claude` را اجرا می‌کند.
3. کنار کد خودش کار می‌کند؛ مصرف از همان سهمیه کم می‌شود و در گزارش‌ها با برچسب `api` دیده می‌شود.

### ۱۲.۳ کاربر عمومی (واحد غیرفنی) — چت ساده
1. لاگین → صفحهٔ چت (بدون IDE، بدون ریپو).
2. گفتگوی جدید می‌سازد، سطح تفکر را انتخاب می‌کند، فارسی می‌نویسد، پاسخ استریم می‌بیند.
3. فایل آپلود/دانلود می‌کند؛ تاریخچهٔ گفتگوهایش را دارد (ایزولهٔ کامل از دیگران).
4. مصرف باقی‌مانده‌اش را در داشبورد شخصی می‌بیند.

### ۱۲.۴ ادمین
1. کاربر می‌سازد/غیرفعال می‌کند؛ ACL مدل و سقف سهمیه و **سقف فضای دیسک** هر کاربر را تعیین می‌کند.
2. داشبورد مصرف کل + drill-down per-user + خروجی CSV.
3. وضعیت اتصال آپ‌استریم و لیمیت اکانت (V6) و ظرفیت ورک‌اسپیس‌های فعال را می‌بیند.
4. audit log را مرور می‌کند.

## ۱۳. معیار پذیرش (Acceptance Criteria)

قالب Given/When/Then برای قابلیت‌های کلیدی. «✅ اثبات‌شده» = با spike سند فنی تأیید شده.

**AC-W (ورک‌اسپیس):**
- با انتخاب ریپو+برنچ، یک کانتینر ایزوله ساخته و ریپو clone می‌شود؛ کاربر دیگری به آن دسترسی ندارد.
- پس از `idle_timeout` بیکاری، ورک‌اسپیس `stopped` می‌شود و volume آن سالم می‌ماند؛ resume بدون clone/نصب مجدد است.
- با عبور مصرف دیسک کاربر از سقف، ساخت ورک‌اسپیس/فایل جدید با پیام فارسی self-service رد می‌شود؛ سیستم خودش چیزی حذف نمی‌کند مگر GC با اخطار قبلی.
- برنچ push‌نشده هرگز بدون اخطار حذف نمی‌شود.

**AC-I (IDE):**
- فقط مالک ورک‌اسپیس می‌تواند `/ide/<id>/` را باز کند؛ کاربر دیگر ۴۰۳ می‌گیرد. ✅ (طراحی auth_request، §۳ فنی)
- IDE بدون پسورد جدا و با نشست EcoCode باز می‌شود.
- workbench کامل زیر پیشوند مسیر بار می‌شود. ✅ (§۳.۱۰ فنی)
- **چت پیش‌فرض = Claude Code**؛ چت Copilot داخلی نمایش داده نمی‌شود. ✅ (spike این جلسه: Copilot حذف، Claude Code افزونهٔ درجه‌یک)

**AC-C (چت/ایجنت):**
- چت وب = اجرای بومی Claude Code (نه CLI-wrapping)؛ tool-use و tool_result کامل کار می‌کند. ✅ (§۰ فنی: opus/sonnet/haiku همه ۲۰۰، حلقهٔ ابزار)
- نوبت مستقل از مرورگر زنده می‌ماند و قابل reattach است (میراث v1).
- افزونهٔ Claude Code با env بدون login تعاملی احراز هویت می‌شود. ✅ (§۳.۱۱ فنی)

**AC-G (گیت‌لب):**
- clone/push فقط با PAT خود کاربر انجام می‌شود؛ commit به نام خودش ثبت می‌شود.
- توکن گیت‌لب فقط داخل sandbox همان کاربر تزریق می‌شود و egress مقصدش را به `git.ecobin.ir` محدود می‌کند.

**AC-V (حاکمیت):**
- مصرف هر سه surface (`web`,`ide`,`api`) در ledger با دو سقف (هفتگی + ۵h) اعمال می‌شود؛ رد با کد و پیام فارسی و زمان آزادشدن.
- ادمین فقط متادیتا/مصرف می‌بیند، نه محتوای گفتگو/ورک‌اسپیس.

**AC-A (کلید CLI):**
- کلید شخصی روی Claude Code واقعی کار می‌کند؛ توکن آپ‌استریم هرگز به کلاینت نمی‌رسد؛ usage از SSE ثبت می‌شود. ✅ (§۰ فنی)

## ۱۶. طرح استقرار و مهاجرت (Rollout)

1. **P0/P1 روی جمع کوچک:** ۲–۳ توسعه‌دهندهٔ داوطلب، ریپوهای غیرحساس؛ جمع‌آوری بازخورد سشن وب.
2. **گسترش dev:** تا زیر ۱۰ نفر؛ فعال‌سازی مسیر CLI (P4a) موازی.
3. **مهاجرت کاربران عمومی (P3):** v2 **کاملاً تمیز** بالا می‌آید (تصمیم ۴)؛ v1 برای یک دورهٔ کوتاه **فقط‌خواندنی** می‌ماند تا کاربران تاریخچهٔ قدیم را ببینند، سپس خاموش می‌شود. بدون انتقال دادهٔ خودکار.
4. **بازگشت (rollback):** چون v1 و v2 ریپو/دیتابیس جدا دارند، در صورت مشکل، v1 دوباره فعال می‌شود بدون از دست رفتن دادهٔ v2.
5. **پیش‌نیاز عملیاتی:** توکن آپ‌استریم زنده (refresh خودکار بک‌اند)، دسترسی به `git.ecobin.ir`، و ظرفیت RAM/دیسک سرور طبق NFR §۷.

| ظرفیت ورک‌اسپیس پر | ساخت/resume با پیام «ظرفیت پر است» صف/رد می‌شود؛ سشن‌های جاری قطع نمی‌شوند. |
| PAT گیت‌لب نامعتبر | clone/push با پیام واضح رد می‌شود؛ کاربر به صفحهٔ پروفایل برای تعویض توکن هدایت می‌شود. |
| سقف سهمیه (هفتگی/۵h) | رد با کد مشخص + زمان آزادشدن؛ ادمین می‌تواند bonus بدهد. |
| سقف دیسک کاربر | مسدود کردن ساخت جدید + راهنمای self-service (حذف/retention). |

## ۱۸. واژه‌نامه

- **Workspace:** واحد اصلی محصول = فضای فایل ایزوله (volume) + کانتینر + ایجنت. دو گونه: ریپویی (dev) و شخصی (عمومی).
- **relay خام:** پروکسی HTTP در بک‌اند که فقط توکن آپ‌استریم را تزریق و درخواست Claude Code را دست‌نخورده عبور می‌دهد (برخلاف CLI-wrapping v1).
- **surface:** منشأ مصرف در ledger — `web` (چت ساده)، `ide` (افزونهٔ داخل کد-سرور)، `api` (کلید CLI روی ماشین dev).
- **egress allowlist:** پروکسی خروجی که مقصد ورک‌اسپیس‌ها را به مجموعهٔ مشخص (relay بک‌اند، `git.ecobin.ir`، `open-vsx.org`) محدود می‌کند.
- **کلید gateway ورک‌اسپیس:** کلید کوتاه‌عمر داخل کانتینر که جای توکن آپ‌استریم می‌نشیند؛ بدترین حالت نشتش = سوزاندن سهمیهٔ خود کاربر.
- **دو سقف:** سهمیهٔ هم‌زمانِ هفتگی + پنجرهٔ غلتان ۵ساعته (میراث v1).
