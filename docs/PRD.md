## ۱. مسئله و انگیزه

سازمان یک اشتراک **Claude Max 20x** خریداری کرده، اما:

- هیچ کنترلی روی **میزان مصرف هر فرد** وجود ندارد؛ یک نفر می‌تواند کل ظرفیت را مصرف کند.
- امکان تعیین اینکه **هر کاربر به کدام مدل‌ها** دسترسی داشته باشد وجود ندارد.
- کاربران **تاریخچه و گزارش مصرف شخصی** ندارند.
- اتصال ابزارهای برنامه‌نویسی (مثل Cline) به اشتراک برای تک‌تک افراد ممکن نیست، مگر با اشتراک‌گذاری مستقیم اکانت که غیرقابل مدیریت است.

**راه‌حل:** یک سرویس لوکال (on-premise) داخل شبکه سازمان که *یک‌بار* به اکانت متصل می‌شود و بین کاربران تعریف‌شدهٔ داخلی، دسترسی کنترل‌شده توزیع می‌کند.

> **توضیح مهم دربارهٔ آپ‌استریم:** سرویس مقصد، Claude خودِ Anthropic نیست؛ یک سرویس ثالث **Claude-سازگار** است (همان API و همان Claude Code CLI با آن کار می‌کند) که اشتراک‌گذاری اشتراک بین کاربران در قوانین آن منعی ندارد. روی سرورِ استقرار، Claude Code یک‌بار به این سرویس لاگین شده و سرویس ما روی همان ماشین بالا می‌آید.

### خارج از محدوده (Non-Goals) — فاز اول

- پشتیبانی از ارائه‌دهنده‌های غیر از آپ‌استریم Claude-سازگار فعلی
- اپ موبایل
- بیلینگ ریالی/مالی بین واحدهای سازمان
- High Availability چند-سروری (مقیاس فعلی: تیم کوچک، یک سرور)
- (اصلاحیهٔ محصول ۱) **محیط اجرای اختصاصی هر پروژه در سندباکس** — سشن کدنویسی وب، کد را می‌نویسد و تست‌های self-contained را اجرا می‌کند؛ بالا آوردن DB/سرویس‌های وابستهٔ هر پروژه در سندباکس فاز اول نیست. تأیید نهایی همیشه با CI خود گیت‌لب و review انسانی روی MR است.
- (اصلاحیهٔ محصول ۱) **جایگزینی CI/CD** — Coolade برنچ می‌سازد و push می‌کند؛ merge به برنچ‌های اصلی فقط از مسیر MR و قواعد خود گیت‌لب.
- (اصلاحیهٔ محصول ۱) **رانر نصب‌شونده روی ماشین توسعه‌دهنده** (اتصال معکوس) — فعلاً لازم نیست چون کد در GitLab است و clone مرکزی مجاز؛ اگر در آینده پروژه‌ای با محیط اجرایی خاص نیاز شد، به‌عنوان گزینهٔ آینده در §۴.۱ ثبت است.

## ۴. معماری کلان (تصمیم‌گرفته‌شده در سطح محصول)

رویکرد: **ترکیبی** — به‌روزشده مطابق TECH v1.6 (حذف LiteLLM) و اصلاحیهٔ محصول ۱:

```
[مرورگر: چت وب]──────────┐
[مرورگر: سشن کدنویسی]────┤                       ┌──▶ [CLI Runner / سندباکس per-session]──▶ [آپ‌استریم
                          ├──▶ [اپ Coolade]──────┤          │  (clone/push)                 Claude-سازگار]
[Claude Code CLI روی      │      │      │        └──▶ [passthrough کلید API]──────────────▶ (همان)
 ماشین توسعه‌دهنده]───────┤      ▼      ▼                   │
[Cline / ابزار دیگر]──────┘  [دیتابیس] [LDAP]         [GitLab سازمان git.ecobin.ir]
                            (کاربر، چت، کلید،
                             مصرف، audit)
```

- **اپ Coolade** = همهٔ منطق گیت‌وی: auth (LDAP + محلی)، ACL مدل، سهمیهٔ وزن‌دار (هفتگی + غلتان ۵ساعته)، ثبت مصرف، چت وب، پنل ادمین، کلیدهای API.
- **منبع حقیقت کد = GitLab سازمان.** هر cloneای (چه در سندباکس مرکزی، چه روی ماشین توسعه‌دهنده) موقتی است؛ خروجی کار ایجنت همیشه به‌صورت برنچ/MR به گیت‌لب برمی‌گردد.
- کاربر و ابزارهایش **هرگز** مستقیم به آپ‌استریم وصل نمی‌شوند مگر از طریق Coolade.

جزئیات فنی (استک، اسکیمای دیتابیس، نحوهٔ اتصال به اکانت Claude) در **سند فنی** توسط مدیر فنی (Opus) تعیین می‌شود.

### ۴.۱ تصمیم معماری تجربهٔ توسعه‌دهنده (اصلاحیهٔ محصول ۱ — رکورد تصمیم)

سؤال: **ایجنت برود پیش کد، یا کد بیاید پیش ایجنت؟** چهار گزینه بررسی شد:

| گزینه | شرح | تصمیم | دلیل |
|---|---|---|---|
| **A — SSH خروجی** | سشن مرکزی به سرور/ماشین توسعه‌دهنده SSH بزند و در پوشهٔ کد او کار کند | ❌ **رد قطعی** | (۱) ابزارهای فایلِ ایجنت (Read/Edit/Grep) لوکال‌اند؛ کار از پشت SSH یعنی همه‌چیز از مسیر شکنندهٔ `bash+ssh/scp` یا SSHFS کُند — عملاً فلج‌کردن ایجنت. (۲) نگهداری کلید SSH به ماشین‌های متعدد روی سرور مرکزی = بزرگ‌ترین blast radius ممکن؛ یک prompt-injection می‌تواند به کل شبکه pivot کند و کل مدل امنیتی سندباکس (egress allowlist) را بی‌اثر می‌کند. |
| **B — اجرای مرکزی** | ریپو از گیت‌لب داخل سندباکس per-session روی سرور Coolade clone شود؛ ایجنت همان‌جا کار کند و به برنچ push کند | ✅ **انتخاب برای مسیر وب (F9)** | زیرساختش (سندباکس اصلاحیهٔ ۶، egress شامل `git.ecobin.ir`) عمدتاً ساخته شده؛ clone مرکزی از نظر سیاست سازمان مجاز؛ git مکانیزم سینک است نه SSH؛ audit و UX وب کامل. محدودیت پذیرفته‌شده: محیط اجرایی اختصاصی پروژه‌ها در سندباکس نیست (Non-Goal). |
| **C — رانر معکوس** | ایجنت سبکی روی ماشین توسعه‌دهنده نصب شود و outbound به پلتفرم وصل شود؛ اجرا لوکال، مدل‌کال از پلتفرم | ⏸ **فعلاً منتفی؛ گزینهٔ آینده** | چون کد فقط در GitLab است و clone مرکزی مجاز، مزیت اصلی‌اش (دسترسی به محیط لوکال) الان خریدار ندارد؛ هزینهٔ ساخت/نگهداری یک کامپوننت توزیع‌شده برای زیر ۱۰ نفر توجیه ندارد. اگر پروژه‌ای با محیط اجرایی خاص نیاز شد، بازبینی می‌شود. |
| **D — CLI روی ماشین توسعه‌دهنده** | توسعه‌دهنده Claude Code CLI را کنار کد خودش اجرا کند؛ `ANTHROPIC_BASE_URL` به گیت‌وی Coolade و auth با کلید شخصی | ✅ **انتخاب برای مسیر CLI (F8)** | ایجنت با تمام قدرت همان‌جایی است که کد و محیط اجرا هست؛ صفر زیرساخت جدید سمت سرور؛ کنترل (سهمیه/ACL/لاگ) در گیت‌وی می‌ماند. پیش‌نیاز فنی: پشتیبانی passthrough از کلاینت Claude Code — ریسک R5. |

## ۵. قابلیت‌ها (Functional Requirements)

### F1 — اتصال به اکانت (ادمین، یک‌بار)
- F1.0: مسیر اصلی: Claude Code روی همان سرور یک‌بار به سرویس Claude-سازگار لاگین شده است؛ سرویس ما از همان اتصال/اعتبارنامهٔ محلی استفاده می‌کند.
- F1.1: مسیر جایگزین: ادمین از پنل، توکن/کلید سرویس را وارد می‌کند (به‌صورت رمزشده روی سرور نگهداری می‌شود).
- F1.2: وضعیت اتصال (متصل/منقضی) در پنل ادمین دیده می‌شود و در صورت انقضا هشدار می‌دهد.
- F1.3: امکان تمدید/اتصال مجدد بدون از دست رفتن داده‌ها.

### F2 — مدیریت کاربران (ادمین)
- F2.1: احراز هویت از طریق **LDAP سازمان**؛ به‌علاوه امکان ساخت **کاربر محلی** مستقل از LDAP (برای مهمان/پیمانکار یا خرابی LDAP).
- F2.2: ساخت، غیرفعال‌سازی و حذف کاربر. غیرفعال‌سازی بلافاصله همهٔ کلیدهای API او را هم باطل می‌کند.
- F2.3: نقش‌ها: `admin` و `user` (فاز اول همین دو نقش کافی است).

### F3 — سیاست دسترسی و سهمیه (ادمین)
- F3.1: به ازای هر کاربر: **لیست مدل‌های مجاز** (مثلاً فقط Sonnet و Haiku؛ Opus فقط برای مدیران فنی).
- F3.2: به ازای هر کاربر: **سقف مصرف دوره‌ای** بر حسب «واحد مصرف» (بخش ۶) با دورهٔ روزانه/هفتگی/ماهانه.
- F3.3: امکان تعریف **گروه/تیم** با سیاست مشترک، برای جلوگیری از تنظیم تک‌تک (nice-to-have فاز اول، الزامی فاز دوم).
- F3.4: با رسیدن به سقف، درخواست‌های بعدی با پیام واضح فارسی رد می‌شوند؛ ادمین می‌تواند سهمیه را موقتاً افزایش دهد.
- F3.5: هشدار به کاربر در ۸۰٪ مصرف (نمایش در وب؛ فاز دوم: ایمیل/پیامک).

### F4 — چت وب (کاربر)
- F4.1: رابط چت فارسی (RTL) با پشتیبانی کامل انگلیسی؛ انتخاب مدل از بین مدل‌های مجازِ همان کاربر.
- F4.2: تاریخچهٔ گفتگو به ازای هر کاربر: لیست گفتگوها، جستجو، تغییر عنوان، حذف. ایزولهٔ کامل بین کاربران.
- F4.3: استریم پاسخ (نمایش تدریجی)، نمایش کد با syntax highlighting و دکمهٔ کپی، رندر Markdown.
- F4.4: آپلود فایل (متن، کد، PDF، تصویر) در گفتگو و دانلود فایل/خروجی تولیدشده.
- F4.5: ادامهٔ گفتگوهای قبلی با حفظ زمینه (context).
- F4.6: **پوشهٔ اختصاصی هر کاربر روی سرور**: هر کاربر یک workspace شخصی دارد؛ سشن‌های چت او در همان پوشه اجرا می‌شوند و فایل‌هایی که در گفتگو تولید می‌شود همان‌جا ذخیره می‌شود. کاربر لیست فایل‌های پوشهٔ خودش را می‌بیند و دانلود می‌کند. ایزولهٔ کامل: هیچ کاربری به پوشه/سشن کاربر دیگر دسترسی ندارد.

### F5 — کلید API شخصی (کاربر)
- F5.1: کاربر از داخل وب، برای خودش کلید API می‌سازد (چند کلید با نام دلخواه، مثلاً «Cline لپ‌تاپ» و «اسکریپت CI»).
- F5.2: کلید فقط یک‌بار هنگام ساخت نمایش داده می‌شود؛ امکان ابطال هر کلید توسط خود کاربر یا ادمین.
- F5.3: مصرفِ همهٔ کلیدهای یک کاربر از **سهمیهٔ همان کاربر** کسر می‌شود و محدودیت مدل‌های او را به ارث می‌برد.
- F5.4: endpoint سازگار با **Anthropic Messages API** و **OpenAI Chat Completions** (هر دو، تا Cline/Continue/aider و اسکریپت‌های OpenAI-سازگار بدون تغییر کار کنند). استریم پشتیبانی می‌شود.

### F6 — داشبورد مصرف
- F6.1 (کاربر): مصرف دورهٔ جاری نسبت به سقف (نوار پیشرفت)، تفکیک به ازای مدل و به ازای کلید، نمودار روند روزانه.
- F6.2 (ادمین): مصرف کل سازمان، رتبه‌بندی کاربران، تفکیک مدل، روند زمانی؛ خروجی CSV.
- F6.3: شمارش مصرف حداکثر با ۱ دقیقه تأخیر به‌روز می‌شود.

### F7 — پنل ادمین
- F7.1: مدیریت کاربران، سیاست‌ها، کلیدها، و وضعیت اتصال به Claude — همه از وب، فارسی.
- F7.2: لاگ رخدادها (audit log): لاگین‌ها، ساخت/ابطال کلید، تغییر سهمیه، رد شدن درخواست به دلیل سقف.

### F8 — مسیر CLI توسعه‌دهنده (اصلاحیهٔ محصول ۱)
- F8.1: توسعه‌دهنده Claude Code CLI را روی ماشین خودش (لپ‌تاپ یا هر سروری که خودش به آن دسترسی دارد) اجرا می‌کند؛ اتصال به مدل فقط از طریق گیت‌وی: `ANTHROPIC_BASE_URL` → آدرس Coolade، auth → **کلید API شخصی** (همان F5).
- F8.2: passthrough باید کلاینت Claude Code را **کامل** پشتیبانی کند: streaming، بلوک‌های tool_use/tool_result، system prompt و هدرهای هویتی خود کلاینت دست‌نخورده به آپ‌استریم برسند (پیش‌نیاز فنی؛ ریسک R5 و راهکار آن).
- F8.3: مصرف این مسیر مثل بقیهٔ کلیدها در ledger ثبت می‌شود و **هر دو سقف** (هفتگی + غلتان ۵ساعته) و ACL مدل همان کاربر اعمال می‌شود؛ در گزارش‌ها با برچسب مسیر (surface) قابل تفکیک است.
- F8.4: صفحهٔ **onboarding** در وب: راهنمای گام‌به‌گام فارسی (نصب CLI، متغیرهای محیطی، ساخت کلید) + قطعهٔ کانفیگ آمادهٔ کپی با آدرس واقعی سرور و کلید تازه‌ساخته‌شده.
- F8.5: هیچ audit سطح فرمان روی ماشین توسعه‌دهنده ادعا نمی‌شود؛ کنترل سازمانی این مسیر = سهمیه + ACL مدل + لاگ metadata درخواست‌ها در گیت‌وی (تصمیم آگاهانهٔ محصول).

### F9 — سشن کدنویسی وب (اصلاحیهٔ محصول ۱)
- F9.1: کاربر در UI وب «سشن کدنویسی» می‌سازد: انتخاب ریپو از میان ریپوهای مجاز او در گیت‌لب سازمان + برنچ مبنا. ریپو به‌صورت shallow داخل سندباکس ایزولهٔ per-session او clone می‌شود (همان envelope اصلاحیهٔ ۶ سند فنی: شبکهٔ internal، egress فقط آپ‌استریم + `git.ecobin.ir`، بدون mount هیچ credential بک‌اند، سقف منابع).
- F9.2: در این نوع سشن، ابزارهای Bash/git ایجنت **فعال** است (برخلاف چت عمومی) — امن است چون کل نوبت داخل سندباکس throwaway اجرا می‌شود.
- F9.3: خروجی کار به برنچ اختصاصی با پیشوند قراردادی (مثل `coolade/<نام-سشن>`) push می‌شود؛ push به برنچ‌های اصلی/محافظت‌شده ممنوع. UI لینک ساخت MR در گیت‌لب را نشان می‌دهد؛ merge فقط از مسیر review خود گیت‌لب (Non-Goal بودن CI/CD).
- F9.4: UI سشن کدنویسی: چت با ایجنت + مرور درخت فایل و diff تغییرات؛ ویرایش دستی فایل‌ها از طریق IDE وب (code-server موجود، پس از per-user شدن) یا ادیتور ساده.
- F9.5: چرخهٔ عمر workspace سشن: پس از پایان/انقضای سشن قابل پاک‌سازی است؛ هیچ تضمین ماندگاری بلندمدت برای clone داده نمی‌شود (منبع حقیقت GitLab است). سیاست نگهداری: قابل تنظیم توسط ادمین، پیش‌فرض در سند فنی.
- F9.6: سقف هم‌زمانی سشن‌های کدنویسی سراسری و قابل تنظیم است (پیش‌فرض متناسب با «زیر ۱۰ توسعه‌دهنده»)؛ درخواست بالاتر از ظرفیت با پیام واضح در صف/رد می‌شود.

### F10 — اتصال گیت‌لب (اصلاحیهٔ محصول ۱)
- F10.1: هر توسعه‌دهنده یک‌بار **توکن گیت‌لب شخصی** (PAT با scope حداقلی read/write repository) را در پروفایل خودش ثبت می‌کند؛ رمزشده ذخیره می‌شود؛ قابل حذف/تعویض توسط خودش.
- F10.2: clone/push هر سشن فقط با توکن **خود همان کاربر** انجام می‌شود — یعنی مجوز دسترسی به ریپوها همان مجوز گیت‌لب خود اوست و commitها به نام او ثبت می‌شود؛ Coolade هیچ توکن سراسری گیت‌لب با دسترسی همهٔ ریپوها نگه نمی‌دارد.
- F10.3: توکن گیت‌لب فقط داخل سندباکس همان سشنِ همان کاربر تزریق می‌شود؛ به لطف egress allowlist حتی در بدترین حالتِ prompt-injection فقط به `git.ecobin.ir` می‌تواند برسد.
- F10.4: لیست ریپوهای قابل انتخاب در UI از گیت‌لب با توکن خود کاربر خوانده می‌شود (جستجو/انتخاب ساده؛ بدون کش بلندمدت).

## ۶. مدل سهمیه: «توکن وزن‌دار»

مصرف هر درخواست = `(توکن ورودی × ضریب ورودی مدل) + (توکن خروجی × ضریب خروجی مدل)`

- ضریب‌ها به ازای هر مدل توسط ادمین قابل تنظیم است؛ پیش‌فرض بر اساس نسبت قیمت API آن مدل‌ها (مثلاً Opus ≈ ۵ برابر Sonnet، Haiku ≈ ۰٫۲ برابر Sonnet).
- واحد نمایش به کاربر: «امتیاز مصرف» (credit) — عدد ساده و قابل فهم، نه توکن خام.
- توکن‌های cache-read با ضریب کاهش‌یافته محاسبه می‌شوند (تشویق به استفادهٔ بهینه).
